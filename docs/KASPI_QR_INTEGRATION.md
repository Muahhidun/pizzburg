# Kaspi QR: состояние интеграции

Актуально на 03.09.2026. Этот документ описывает наш код и принятый порядок;
Public QR API и ответы рабочей группы Kaspi остаются источником точных адресов,
полей и визуальных требований.

## Что фиксировано продуктом

- Для клиента это одно заведение, одно приложение, одно меню и одна оплата.
  Разделение заказа между аккаунтами Poster — внутренняя маршрутизация и к
  Kaspi не относится.
- Kaspi появляется в приложении только после готовой сквозной интеграции.
- Мобильное приложение использует платёжную ссылку, web — QR.
- Оплата подтверждена только серверным статусом `Processed`. Возврат в наше
  приложение после deep link ничего сам по себе не подтверждает.
- После `Processed` клиент видит 60 секунд на отмену. Затем кнопка исчезает,
  идёт 10 секунд технического буфера, и на 70-й секунде заказ отправляется в
  Poster. До этого кассир заказ не видит.
- Отмена оплаченного заказа создаёт полный возврат. Админка также поддерживает
  частичный возврат и ручной повтор неудавшейся операции.

## Сертификат: принятое решение

Общий сертификат между нашей платформой и SmartPicasso не используется.
SmartPicasso отказался от параллельной работы с одним комплектом из-за границ
ответственности и возможных разногласий по платежам. Подтверждено, что выпуск
нового сертификата отзывает действующий старый сертификат.

Порядок один:

1. Довести iOS и Android до готовности к публикации.
2. Согласовать окно со SmartPicasso: они снимают свои приложения со сторов.
3. Вручную выпустить наши приложения без онлайн-Kaspi и передать ссылки Kaspi.
4. После проверки приложений получить новый боевой сертификат для нашей
   платформы и быстро включить уже подготовленную интеграцию.

После перевыпуска онлайн-Kaspi в старом приложении перестаёт работать. Для
оставшихся пользователей SmartPicasso временно доступны карта, наличные и
Kaspi через терминал на месте. Новый private key и сертификат остаются только
в нашей инфраструктуре и не передаются SmartPicasso.

## Что уже реализовано

Миграция `20260830120000_payment_foundation` добавляет:

- `PaymentAttempt` — каждую отдельную ссылку/QR и статусы Kaspi;
- `PaymentRefund` — полный или частичный возврат, сумму, инициатора, повторы;
- `PaymentEvent` — безопасный технический журнал без платёжных секретов;
- точные `paidAt` и `cancelUntil` у заказа;
- статусы заказа `REFUND_PENDING`, `PARTIALLY_REFUNDED`, `REFUNDED`,
  `REFUND_FAILED`.

`PaymentsService` умеет:

- создавать и синхронизировать попытку через интерфейс provider-а;
- открывать окно отмены только после `Processed`;
- не допускать неоплаченный Kaspi-заказ в Poster;
- создавать идемпотентный полный возврат при отмене;
- ограничивать сумму частичных возвратов остатком оплаты;
- повторять временно неудавшийся возврат с паузой 1, 2, 4… до 60 минут;
- после восьми неудач оставлять видимую ошибку и ручной повтор в админке.

01.09.2026 добавлен настоящий provider третьей схемы Public QR API:

- режимы `disabled` / `test` / `production` и жёсткая защита от смешивания
  тестового и боевого URL;
- mTLS из `.pfx`/`.p12` либо пары PEM certificate + private key; секреты
  принимаются только через base64-переменные окружения;
- `qr/create-link` для телефона, `qr/create` для web, status v02 и refund;
- Int64 Kaspi сохраняются строками без потери точности JavaScript;
- коды ошибок разделены на временные и постоянные для безопасных повторов;
- клиентские маршруты закрыты JWT и проверкой владельца заказа;
- серверный poller использует `StatusPollingInterval` и продолжает работу,
  даже если клиент закрыл приложение после перехода в Kaspi.kz.

Тестовый комплект Kaspi хранится только в игнорируемом `tmp/` с правами
`600/700`. В тестовом контуре реальным mTLS-запросом выполнена цепочка:
регистрация устройства → создание оплаты → scan → Wait → confirm → Processed.
Тест refund вернул предусмотренный протоколом временный код `-99000006`; код
правильно поставил такую операцию на повтор. Реальных денег и Poster тест не
касался.

Во Flutter добавлены модель/API и состояния мобильной оплаты: открытие ссылки,
фоновый опрос, ожидание, успех, ошибка и повтор. Способ скрыт двумя независимыми
предохранителями: настройкой `payments.kaspiOnline=false` на сервере и
compile-time флагом `KASPI_BRAND_ASSETS_READY=false` в store-сборке.

Админка показывает состояние денег отдельно от статуса заказа, историю
возвратов, ошибку и следующую попытку. Для подтверждённой оплаты доступны
полный/частичный возврат и повтор операции.

## Почему это пока безопасно

Production по умолчанию продолжает использовать `KASPI_MODE=disabled` и
`DisabledKaspiProvider`: без явной конфигурации он не делает сетевых запросов.
Способ `KASPI_ONLINE` скрыт настройкой доступности и отдельным флагом мобильной
сборки. Сертификаты, private key, пароль, DeviceToken и платёжные ссылки не
пишутся в Git и журнал событий.

## Что останется после получения доступа

1. Получить официальные кнопки, логотипы Gold/Red+ и QR-шаблон; доступ к
   присланной Figma сейчас не даёт чтение через API.
2. Согласовать с Kaspi мобильные состояния и будущий web QR.
3. После публикации и проверки Kaspi получить новый рабочий сертификат,
   проверить цепочку, пароль, срок и ограничения статического исходящего IP
   нашей инфраструктуры без вывода секретов.
4. Вместе с Kaspi повторить scan/confirm/error/refund уже на согласованной
   сборке и сверить журнал операций.
5. Только после этого включить оба флага и выпустить обновление в сторах.
