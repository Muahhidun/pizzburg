# Напитки WeDrink: заказы доставки прямо на кассу WDrink

Начато 25.11.2026. Решение — `DECISIONS.md` §15, этап — `ROADMAP.md` этап 8.
Вторая половина работы — в репозитории `Muahhidun/zakupwedrink`,
файл `docs/pizzburg-delivery-module.md`. Раздел «Договорённость между
системами» в обоих файлах одинаковый: меняется только вместе.

## Зачем

Сейчас напитки WeDrink заведены товарами в Poster «Sunday». Заказ с напитками
падает на планшет Sunday, кассир печатает бегунок и несёт его в WeDrink,
кассир WeDrink пробивает напитки на своей кассе вручную, бариста готовит,
напитки несут обратно в Sunday, оттуда забирает курьер. Вечером деньги за
напитки сводят руками.

Нужно: напитки остаются в приложении как были, но их часть заказа уходит
сразу на моноблок кассы WDrink. Sunday к напиткам отношения больше не имеет.

## Как будет работать

1. Клиент заказывает пиццу и молочный чай. Заказ делится на части, как сейчас:
   еда — в Poster «Основной» / «Sunday», напитки — третьим отделом на кассу
   WDrink.
2. Часть WDrink уходит в тот же момент, что и части Poster (после окна отмены
   и подтверждённой оплаты Kaspi). Предзаказ — за 15 минут до времени
   (настройка отдела): напитки быстро остывают и тают.
3. На кассе WDrink всплывает окно «Доставка PizzBurg №1234» — только номер,
   напитки, количество. Ни телефона, ни адреса, ни комментария клиента:
   WeDrink готовит строго по рецепту и отдаёт.
4. Кассир нажимает «Принять» → печатаются бегунок и наклейки, продажа сама
   проходит на кассе WDrink способом «Доставка PizzBurg», склад списывается.
   Или «Нет позиции…» → включается наш обычный сценарий нехватки (§12.9).
5. Сотрудник WeDrink относит напитки на раздачу PizzBurg. Отдельной кнопки
   «готово» на кассе WDrink нет: готовность всего заказа отмечает раздача
   на своём планшете, как сейчас.
6. Не приняли за 5 минут — напоминание в группу кассы, за 10 — руководству
   (это уже делает `AcceptReminderService`, для отдела WDrink он работает так же).
7. Заказ отменили после «Принять» → на кассе WDrink окно «Заказ №1234 отменён —
   не готовьте» и одна кнопка «Понятно». Продажа на кассе WDrink сторнируется.

## Деньги

- Клиент платит PizzBurg как сейчас: Kaspi онлайн приходит на Kaspi PizzBurg,
  наличные курьер сдаёт кассиру PizzBurg вместе со всем остальным.
- В 21:30 (конец смены PizzBurg, время берём из настроек) в группу кассы
  уходит «Отдать WeDrink за напитки: 15 000 ₸ (наличные 5 000, онлайн 10 000)».
  Кассир PizzBurg отдаёт WeDrink 15 000 наличными.
- Сумма — полная цена принятых напитков по меню WDrink. Скидки, баллы и
  подарки по акциям — расход PizzBurg: WeDrink получает за напиток всегда
  полную цену (иначе их касса не сойдётся).
- Фискальный чек за напитки WDrink не пробивает: оплату фискализирует PizzBurg
  (Kaspi или наличный чек), как и сейчас.

## Меню в приложении

- В меню WDrink владелец точки отмечает, какие напитки идут в доставку
  (мороженое в рожке и сандэ — нет). Цены — те же, что в зале.
- Наш синк забирает этот список так же, как меню Poster: категории и товары
  отдела WDrink. Витринные поля (имя, фото, порядок, категория, стоп) остаются
  нашими и синком не трогаются.
- **Напитки в приложении не пропадают.** Нынешние товары напитков (сейчас
  они в отделе Sunday) не удаляются и не создаются заново: скрипт перевешивает
  те же записи на отдел WDrink. Фото, описания, избранное, история заказов
  и порядок витрины сохраняются.

## Что меняется в коде PizzBurg

| Где | Что |
|---|---|
| `prisma/schema.prisma` | `PosterAccount.kind` (`POSTER` по умолчанию, `WDRINK`), `PosterAccount.apiUrl` (адрес сервиса WDrink). Ключ кладём в существующее поле `token`, как токены Poster. Миграция только добавляет колонки |
| `src/wdrink/wdrink.client.ts` | Новый клиент API WDrink: меню, заказ, статус, отмена |
| `poster/poster-sync.service.ts` | Ветка по `kind`: для WDRINK меню берётся из WDrink |
| `orders/orders.service.ts` → `dispatchToPoster` | Ветка по `kind`: часть WDRINK уходит в WDrink. Учитывает `POSTER_DRY_RUN=1` так же, как Poster |
| `orders/orders.service.ts` → `syncStatus`, `orders/shortage.service.ts` | Статус части WDRINK читается из WDrink. «Нет позиции» с кассы → `markUnavailable`. Повторная отправка после нехватки отменяет прежний заказ в WDrink сама — кассиру отклонять ничего не нужно |
| Отмена заказа (`setStatus` → CANCELLED) | Части WDRINK отправляется отмена |
| Предзаказ | Часть WDRINK ждёт до `scheduledAt − leadMinutes` |
| `couriers/dispatch-board.service.ts` | На плитке позиции WDrink подписаны «WeDrink» и видно, приняла ли касса WDrink |
| `orders/daily-summary.service.ts` | В 21:30 — сообщение «Отдать WeDrink» в группу кассы |
| Админка → Настройки → Отделы | Подключение отдела WDrink: адрес и ключ из кабинета WDrink |
| `scripts/` или `prisma/` | Перенос товаров напитков из Sunday в отдел WDrink: пробный прогон по умолчанию, запись с `--apply` |

Без отдела вида WDRINK ни одна новая ветка не срабатывает: для других
заведений ничего не меняется.

## День перехода

Порядок важен: иначе напиток либо пропадёт из приложения, либо пробьётся дважды.

1. Всё выложено, касса WDrink обновлена на моноблоке, модуль включён для точки
   в кабинете WDrink, список напитков для доставки отмечен.
2. В админке PizzBurg подключён отдел WDrink (ключ), синк прошёл, видно
   сопоставление напитков.
3. Пробный прогон переноса → проверка вами → `--apply`. С этой минуты напитки
   уходят на кассу WDrink:
   ```bash
   cd backend
   railway ssh --service backend --environment production -- node dist/wdrink/relink-cli.js --from SunDay --category WeDrink --to WeDrink
   # проверить список пар и цен, затем то же самое с --apply
   ```
   Пары подбираются по названию; если какую-то не нашло — `--map "'<имя в приложении>=<номер позиции WDrink>'"`.
   Напитки, которых в приложении ещё не было, синк заводит **скрытыми**:
   новинку владелец включает в витрине сам.
4. Удалить категорию WeDrink из Poster Sunday (не раньше шага 3).
5. Кассиров WeDrink предупредить: бегунки из Sunday больше не придут, вручную
   доставку не пробивать — касса делает это сама.
6. Первый день — смотреть тревоги и сверку в 21:30.

## Проверка без боевых систем

`POSTER_DRY_RUN=1` выключает и отправку на кассу WDrink. Чтобы гонять
настоящий обмен с локальным WDrink при выключенном Poster, добавьте
`WDRINK_DRY_RUN=0`.

- PizzBurg с `POSTER_DRY_RUN=1` и временной базой.
- WDrink — локально или демо-касса, модуль включён только у тестовой точки.
- Сценарии: обычный заказ, общий заказ еда+напитки, предзаказ, «нет позиции»,
  отмена до и после «Принять», касса WDrink без интернета, сверка в 21:30.

## Договорённость между системами

> Одинаковый текст в PizzBurg (`docs/WDRINK_INTEGRATION.md`) и WDrink
> (`docs/pizzburg-delivery-module.md`). Меняется только в обоих сразу.

**Адрес:** `https://<сервис WDrink>/api/partner/v1/…`

**Доступ:** заголовок `Authorization: Bearer <ключ>`. Ключ выдаёт кабинет
WDrink точке с включённым модулем (показывается один раз, в базе WDrink
хранится только его хэш). По ключу WDrink определяет точку. Ключ вводится в
админке PizzBurg при подключении отдела. В git, логи и сообщения не попадает.

**Деньги** — целые тенге.

### `GET /menu`

Напитки, отмеченные точкой для доставки.

```json
{
  "categories": [{ "id": "12", "name": "Молочный чай", "sort": 3 }],
  "items": [
    { "id": "345", "category_id": "12", "name": "Таро 0,7 холодный",
      "price": 1800, "sort": 1, "available": true }
  ]
}
```

`id` — строка (номер позиции меню WDrink). Позиция, которую сняли с доставки
или удалили, просто не приходит — PizzBurg её деактивирует.

### `POST /orders`

```json
{
  "external_id": "ckx…:1",
  "number": 1234,
  "items": [{ "item_id": "345", "qty": 2, "price": 1800 }],
  "show_at": "2026-11-25T13:15:00Z"
}
```

- `external_id` — номер части в PizzBurg; повтор с тем же `external_id`
  ничего не создаёт и возвращает тот же заказ.
- `price` — цена, которую видел клиент. Если она не совпала с меню WDrink —
  ответ `409 PRICE_MISMATCH` (меню разъехалось, нужен синк).
- `show_at` — необязательное; раньше этого времени касса окно не показывает.

Ответ: `{ "id": "…", "status": "NEW" }`.

### `GET /orders/{external_id}`

```json
{
  "status": "NEW | ACCEPTED | SHORTAGE | CANCELLED",
  "accepted_at": "…",
  "unavailable_item_ids": ["345"]
}
```

- `SHORTAGE` — кассир нажал «Нет позиции» и отметил позиции. Остальное
  в заказе не готовится, пока PizzBurg не пришлёт новый состав.
- PizzBurg опрашивает раз в минуту, как Poster.

### `POST /orders/{external_id}/cancel`

`{ "reason": "CUSTOMER | REPLACED | VENUE" }`. Если заказ уже принят — на
кассе всплывает окно «отменён — не готовьте», продажа сторнируется. `REPLACED`
— после нехватки PizzBurg прислал новый состав новым `external_id`: окна об
отмене нет, касса просто показывает новый заказ.

### `GET /status`

`{ "online": true, "last_seen": "…" }` — есть ли на связи касса точки
(видели за последние 2 минуты). PizzBurg показывает это в консоли и
поднимает тревогу, если касса пропала в рабочее время.

### Ошибки

`401` — неверный ключ, `403 MODULE_DISABLED` — модуль выключен у точки,
`404` — нет такого заказа, `409` — конфликт (цена, уже отменён), `422` —
неверные данные. Тело: `{ "error": "CODE", "message": "по-русски" }`.
