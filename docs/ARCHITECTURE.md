# PizzBurg Delivery — архитектура

Замена арендного приложения FoodPicasso/SmartPicasso собственной платформой.
Проектируется сразу как **мультитенантная** — в перспективе платформу можно
предлагать другим заведениям (модель SmartPicasso).

## Стек

| Слой | Технология | Почему |
|---|---|---|
| Бэкенд API | NestJS (TypeScript) + PostgreSQL + Prisma | Зрелый мейнстрим, структура модулей, легко поддерживать соло |
| Мобильное приложение | Flutter | Визуал уровня Додо: кастомные анимации, один код iOS+Android |
| Админка | Next.js (React) | Позже, фаза 3; до неё хватает Poster + минимальных экранов |
| Хостинг | Railway (как WDrink) | Уже знакомо, Postgres там же |
| Пуши | Firebase Cloud Messaging (FCM) | Бесплатно, iOS+Android |
| Оплата | Kaspi Pay (договор мерчанта) | Стандарт в КЗ; до подключения — наличные/карта при получении |
| SMS OTP | Mobizon или аналог | Только регистрация; потом можно заменить WhatsApp-кодом |
| Карты/зоны | 2ГИС или Яндекс (бесплатные лимиты) | Проверка адреса в полигоне зоны |

## Монорепозиторий

```
pizzburg/
  backend/    NestJS API + Prisma (единый для клиентского приложения и админки)
  mobile/     Flutter-приложение клиента
  admin/      Next.js админка (фаза 3)
  docs/       документация
```

## Мультитенантность

Каждая строка бизнес-данных принадлежит `Tenant` (заведение-бренд).
У тенанта несколько `Venue` (точек). Изоляция — по `tenantId` во всех
запросах (Prisma-мидлвар). Один деплой обслуживает всех тенантов;
мобильное приложение собирается per-tenant (белая этикетка: цвета,
логотип, `tenantSlug` в конфиге сборки).

## Интеграция Poster POS

**У тенанта несколько аккаунтов Poster** (модель `PosterAccount`) — это
отделы со своими планшетами: «Основной» (фастфуд) и «Sunday» (суши/роллы,
аккаунт «PizzBurg кафе»). Меню обоих отделов сливается в одно для клиента;
при оформлении заказ расщепляется по отделам (`OrderDispatch`): пицца
уходит на планшет основного отдела, роллы — на планшет Sunday. Статус
заказа для клиента — агрегат по всем отправкам.

Poster — источник правды по меню и получатель заказов:

1. **Синк меню**: `menu.getCategories` + `menu.getProducts` → таблицы
   Category/Product (посерийный `posterId` для сопоставления). Фото, цены,
   стоп-листы. Запуск: вручную из админки + по расписанию (15 мин).
2. **Отправка заказа**: после оформления — `incomingOrders.createIncomingOrder`
   (телефон, состав, тип, адрес, комментарий). `posterOrderId` сохраняем
   для отслеживания статуса.
3. Токен — в `.env` (`POSTER_TOKEN`), для SaaS-режима — поле у тенанта.

## Жизненный цикл заказа

```
Клиент (Flutter) → POST /orders → валидация зоны/времени/минималки
  → расчёт (сумма, доставка, промокод, баллы)
  → создание Order (status NEW) → отправка в Poster
  → пуш клиенту при смене статуса (ACCEPTED → COOKING → ON_WAY → DELIVERED)
```

Статусы из Poster подтягиваем поллингом/вебхуком (уточнить доступность
вебхуков на тарифе Poster).

## Лояльность (паритет с FoodPicasso)

- Кешбэк баллами: уровни (3/5/7% — настройка тенанта), 1 балл = 1 ₸.
- Начисление после выполнения заказа, списание — при оплате следующего.
- Промокоды: фикс/процент/подарок (2+1 реализуем как «подарочная позиция»).
- Реферальная программа — фаза 4.

## Фазы

- [ ] **Фаза 1 — ядро (4–6 недель)**: синк меню из Poster, каталог,
      корзина, оформление (доставка/самовывоз, предзаказ), оплата
      наличными/картой при получении, заказ в Poster, OTP-авторизация.
      Клиент — Flutter Web (PWA) с тем же кодом, что и будущая мобилка.
- [ ] **Фаза 2 — сторы и пуши (3–4 недели)**: сборки iOS/Android,
      публикация, FCM-статусы заказа, история заказов.
- [ ] **Фаза 3 — оплата и зоны**: Kaspi Pay онлайн, полигоны зон доставки
      с разной стоимостью/минималкой, админка (меню-оверрайды, стоп-лист,
      заказы, настройки).
- [ ] **Фаза 4 — удержание**: баллы и уровни, промокоды, сторис-акции,
      рефералка, пуш-рассылки по сегментам, отзывы.
- [ ] **Фаза 5 — миграция**: импорт базы клиентов (+балансы баллов),
      SMS/пуш-кампания перехода, 1–2 мес параллельной работы со старым
      приложением, отключение FoodPicasso.
