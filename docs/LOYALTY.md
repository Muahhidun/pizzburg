# Кэшбэк собственного приложения

Лояльность Poster и его автоматические 7% не участвуют в этой системе.
Единственный баланс клиента — `Customer.pointsBalance`, а каждая операция
фиксируется в `LoyaltyTransaction`.

## Правила

- 1 балл = 1 ₸.
- Процент задаётся в админке: **Настройки → Кэшбэк приложения**.
- По умолчанию — 3%.
- Кэшбэк начисляется один раз, когда заказ получает статус `DELIVERED`.
- База начисления: оплаченные товары без доставки и без части, закрытой
  баллами. Подарки акции в базу не входят.
- Баллами можно оплатить товары вплоть до 100% их стоимости, но не доставку.
- Списание доступно только после OTP-входа и только для номера профиля.
- В Poster товары всегда уходят по полной цене. Подарки и списанные баллы
  суммируются в оплате «Личная интеграция» отдельно по каждому отделу.
- При отмене заказа списанные баллы возвращаются один раз.
- Повторные и параллельные запросы начисления/возврата сериализуются
  блокировкой строки заказа и проверкой операции `orderId + type`.

## Что видит пользователь

- Кнопка профиля в каталоге и OTP-вход.
- Текущий баланс, процент и журнал начислений/списаний.
- Поле использования баллов при оформлении.
- Предварительный расчёт будущего кэшбэка.

## Что доступно администратору

- Процент кэшбэка в настройках.
- Баланс и полный журнал в карточке клиента.
- Ручная корректировка со знаком `+`/`-` и обязательной причиной.
- Ручное продвижение статусов заказа. Статус «Доставлен» запускает
  начисление.

## Проверка на staging

**Пройдена 09.08.2026.** Контрольный заказ №6: товары 5 850 ₸,
списано 500, к оплате 5 350, после доставки начислено 160 баллов.
Контроль отмены №7: списано 300, после отмены возвращено ровно 300.
Баланс прошёл цепочку `1000 → 500 → 660 → 360 → 660`, а отменённый
заказ исключился из выручки админки.

1. Убедиться, что `POSTER_DRY_RUN=1` и `OTP_DEV_MODE=1`.
2. В админке открыть клиента и начислить ему, например, `+1000` с причиной
   «Тест staging».
3. В веб-приложении войти по этому же телефону через OTP.
4. Положить товары в корзину, списать часть баллов и оформить заказ.
5. Проверить в админке сумму заказа и строку «Списано баллов».
6. Нажать последовательно «Принять» и «Доставлен».
7. Проверить новый баланс и одну операцию `EARN`. Повторное открытие или
   повторный запрос статуса не должен начислить баллы второй раз.
8. Отдельный сценарий: оформить заказ с баллами и отменить его — баланс
   должен восстановиться одной операцией возврата.

Перед боевым включением сделать один согласованный заказ и сверить чек:
`Личная интеграция = стоимость подарков + потраченные баллы`.

## Импорт балансов старого приложения

Нужен CSV с колонками `phone,points,name`. Понимаются также `;`, tab и
русские заголовки `телефон,баланс,имя`. Бонусы Poster сюда не загружать.
Телефон и баланс обязаны находиться в одной строке: соединение отдельных
выгрузок по имени запрещено из-за дублей и несовпадений.

```bash
cd backend

# Только план и отчёт об ошибочных строках — ничего не меняет
npm run loyalty:import -- /полный/путь/balances.csv \
  --batch=legacy-2026-08

# Применение после проверки отчёта
npm run loyalty:import -- /полный/путь/balances.csv \
  --batch=legacy-2026-08 --apply
```

Импорт нормализует казахстанские телефоны, создаёт отсутствующих клиентов,
приводит баланс к значению из выгрузки и пишет `ADJUST` в журнал. Повторный
запуск того же `--batch` пропускает уже обработанных клиентов.
