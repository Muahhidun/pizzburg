## Зачем этот проект

PizzBurg (Экибастуз, Казахстан; фудкорт ТРЦ MaxiMall) 4 года арендует
white-label приложение доставки у FoodPicasso/SmartPicasso:
~195 000 ₸/мес + ~20 000 ₸ SMS. С 01.08.2026 тарифы растут на 15–20%
(новая сетка: оборот до 12 млн — 235 000 ₸/мес, до 18 млн — 285 000 ₸/мес).
Скидку дать отказались. Решение: собственная платформа.

Владелец (Дом) — технически подкован: в одиночку с ИИ-агентами построил
wdrink.kz (склад/финучёт общепита, Railway), заменил им R-Keeper.
Объёмы: ~80 заказов/день (50–60 доставка), ~14 900 клиентов в выгрузке.

**Стратегическая цель**: платформа мультитенантная с первого дня — позже
предлагать её другим заведениям (модель самого SmartPicasso).

## Главные принципы (сформулированы владельцем)

1. Не копировать SmartPicasso слепо — понять механику и сделать лучше.
2. Касса Poster — источник правды по товарам/ценам/стоп-листам. Витрина
   приложения — полностью независимый слой поверх (свои категории,
   имена, описания, порядок, видимость), правится в своей админке,
   но каждая позиция навсегда привязана к позиции Poster.
3. Два отдела = два аккаунта Poster («Основной» — фастфуд, «Sunday» —
   суши/роллы/кофе/WeDrink). Клиент видит одно меню; заказ при
   оформлении расщепляется на два планшета.
4. **Сходимость смены — святое.** Всё, что видит клиент в приложении,
   должно совпасть с тем, что пробито в Poster. Вечером кассир сверяет:
   выручка Poster = наличные + мелочь + Kaspi-терминал + Halyk-терминал
   + Wolt + «Личная интеграция».

## Ключевое открытие: механика «Личной интеграции»

Как FoodPicasso добивается сходимости (подтверждено чеками):
все позиции пробиваются по полным кассовым ценам (включая подарочные
по акции), реальные деньги клиента идут своим методом оплаты, а вся
«виртуальная» часть (скидка акции, оплата баллами, онлайн-оплата)
передаётся как предоплата `payment{type,sum}` в createIncomingOrder —
в чеке Poster она отображается методом «Личная интеграция».
Пример: 2+1 пицца = чек 8850 ₸, из них «Карточкой 6300» + «Личная
интеграция 2550». Недостачи нет, акция видна, склад списан верно.

Мы используем ровно эту же механику.

## Что уже открыто/решено (реестр решений)

- **Комбо** смоделированы в самом Poster: тех.карта («Комбо Донер» 2290 ₸)
  с наборами модификаторов по 0 ₸ (Донер маленький + Кола 0,5 + Фри).
  Синк забирает `group_modifications` → приложение рендерит выбор,
  заказ уходит с модификаторами → чек и склад сходятся сами.
  Виртуальные категории SmartPicasso («Основное блюдо», «Напиток»,
  «Добавка» с нулевыми позициями) НЕ нужны — они существовали только
  в их админке, в Poster их нет.
- **Акции** существуют и в Poster (Маркетинг → Акции, «2+1 Пицца»:
  ровно 2 шт из «Пиццы» → Маргарита −100%, без накопления, много раз
  в чеке, вручную кассиром). Наш промо-движок повторяет правило в
  корзине приложения; в Poster скидка уходит «Личной интеграцией».
- **Цены по источникам**: в Poster у товара бывают спеццены по источникам
  заказов (Wolt +100–200 ₸ для компенсации комиссии). В приложении цена
  = цене зала; на будущее — наценка приложения (поле priceOverride уже
  есть + идея глобальной наценки в настройках тенанта).
- **Статусы**: онлайн-заказ падает на оба планшета сразу (+ Telegram-бот
  как страховка). Каждый отдел жмёт «Принять» у себя. Пуш клиенту — по
  «главному» отделу (при общем заказе — Основной), чтобы не спамить.
  Бэкенд поллит incomingOrders.getIncomingOrder (0=NEW, 1=ACCEPTED,
  7=REJECTED) и агрегирует.
- **Чек и курьер**: кассир закрывает заказ с оплатой сразу при принятии —
  курьеру нужен бумажный чек. Принятие-без-закрытия станет возможным
  только с курьерским приложением (тогда закрытие после доставки).
- **Оплаты приложения**: наличные курьеру / карта курьеру (терминал
  с собой) / Kaspi онлайн (redirect с суммой; договор эквайринга
  оформлен на юрлицо владельца — счёт его, можно переиспользовать).
- **Доставка**: зон нет (город маленький). Минималка 1200 ₸ (ниже —
  только самовывоз), доставка 600 ₸, бесплатно от 5000 ₸. Всё в
  `Tenant.settings.delivery`, должно быть редактируемо в админке.
  Полигоны зон в схеме есть (DeliveryZone) — для других городов/SaaS.
- **Миграция клиентов**: выгружены весь список клиентов + заказы за
  60 дней. Телефон = идентификатор → профили сохранятся. Проверить
  наличие балансов баллов в выгрузке; иначе стартовый бонус за переезд.
- **Хедж по деньгам**: оплата FoodPicasso до конца 2026 фиксирует старые
  тарифы — оплачивать помесячно, пока своё не готово; 1–2 мес
  параллельной работы, пуш/SMS-кампания перехода, бонус за установку.

## Витрина (текущее состояние правил)

- Скрыты: КидсБокс (до поставки боксов), Суши Холодные (старая),
  Напитки Кола (Sunday; напитки берём с основного).
- «Суши холодные 2026» → на витрине «Роллы».
- «Закуски-Фри» (Sunday): видимы только Стрипсы и Луковые кольца,
  остальное — с основного отдела.
- «Добавки к блюдам» двух отделов слиты в одну витринную категорию.
- Порядок категорий владелец расставит сам (CLI `order`, позже админка).
- Товары из скрытых в кассе категорий («Половинки пицц») не продаются.

## Идеи / заметки на подумать

- Наценка приложения: Poster API отдаёт у товара поле `sources`
  [{id, name, price, visible}] — спеццены по источникам заказов (Wolt
  видно уже сейчас). Если завести источник «Приложение» в Poster, синк
  сможет брать цену оттуда штатно (либо наша наценка поверх — на выбор).
- Автопривязка новых товаров кассы в правильную витринную категорию
  работает по категории Poster; для «общих» позиций двух отделов
  (фри и т.п.) достаточно скрыть дубль один раз — синк это не отменит.
- Poster createIncomingOrder имеет поле `promotion` — потенциально можно
  передавать акцию Poster напрямую вместо «Личной интеграции»; проверить
  на тесте, что даёт лучший чек (пока — интеграция, как у FoodPicasso).
- Wolt-подобные агрегаторы не трогаем — их интеграция уже в Poster.
- В FoodPicasso есть «Магазин улучшений», «Smart рекомендации в корзине»,
  чаевые — кандидаты в бэклог после паритета.
- QR-меню для зала — у Poster есть своё (Poster QR); не наш приоритет.

## Технический контекст

- Репозиторий: `~/Приложение доставки/pizzburg` (git, ветка main).
- `backend/` — NestJS + Prisma + PostgreSQL (локальная БД `pizzburg`).
  Запуск: `backend/dev.sh` (убивает процесс на :3210 и стартует;
  `pkill` по имени НЕ находит процесс — не использовать).
- `.env`: `POSTER_DRY_RUN=1` — заказы НЕ уходят на планшеты (баннер
  режима печатается при старте). Боевой режим — только по договорённости
  с владельцем.
- Схема БД: два слоя меню (Category/Product — зеркало Poster;
  AppCategory + витринные поля Product — наш слой). PosterAccount —
  отдел с токеном. OrderDispatch — часть заказа в конкретный отдел.
- Синк каждые 15 мин + `POST /poster/sync/:tenantId`.
- Меню: `GET /menu/:tenantSlug`. Заказ: `POST /orders/:tenantSlug`.
  Статусы: `POST /orders/by-id/:id/sync-status`.
- Витрина из CLI: `npx tsx prisma/storefront.ts list|order|hide|...`
- Аккаунты Poster добавляются: `npx tsx prisma/add-poster-account.ts`.
- Цены Poster приходят в сотых → делим на 100 (`PosterClient.toTenge`).
- tsx НЕ поддерживает decorator metadata → dev через ts-node (это уже
  настроено, не менять на tsx).
- `prisma db push` используется в разработке; перед первым деплоем
  создать чистую миграцию. ВНИМАНИЕ: `db push --accept-data-loss`
  сносит посторонние таблицы в БД.
