# Wolt Drive — резервный курьер

Актуально на 29 сентября 2026 года.

## Зачем он нужен

Wolt Drive — не ещё один способ доставки в клиентском приложении, а
резерв для кассы. Клиент оформляет обычный заказ. Если свободного
своего курьера нет, кассир вызывает Wolt из нашей админки.

Эта доработка не меняет Android/iOS-сборки и не мешает проверкам в
App Store и Google Play.

## Рабочий сценарий

1. В «Кассе» открывают доставочный заказ и нажимают `Wolt Drive`.
2. Указывают время готовности еды от 5 до 60 минут и число пакетов.
   По умолчанию стоит 5 минут для уже готового заказа; ждём от Wolt
   письменного подтверждения минимума для production.
3. Кнопка «Рассчитать» запрашивает binding shipment promise и показывает
   стоимость, подачу и оценку времени до клиента. Курьер ещё не вызван.
4. Кассир отдельно подтверждает платный вызов. Повторное нажатие от
   двойного вызова защищено атомарной сменой статуса в базе.
   Если quote выше 2 000 ₸, кнопка вызова блокируется, а backend повторно
   отклоняет платной вызов.
5. В админке сохраняются Wolt order reference, статус и tracking URL. Клиенту
   Wolt может отправить SMS со ссылкой на отслеживание.

## Доступы и режимы

В публичной документации нет готовых токенов. Статус доступов:

- development Merchant Key (Bearer token) — получен 04.09.2026;
- test Venue ID для точки забора — получен 04.09.2026;
- Merchant ID для подключения webhook — получен 04.09.2026;
- production Merchant Key, Merchant ID и Venue ID для Экибастуза — получены;
- cash collection для тестового мерчанта выключен и пока сознательно отложен;
- тестовый ресторан и разрешённая зона находятся в Алматы.

Реквизиты сохранены только в локальном ignored-файле и локальной базе, режим
строго `test`; значения в Git и документации не записаны. Авторизация на
development API подтверждена: сервер принял Bearer token и Venue ID. Тестовый
ресторан привязан к адресу Достык, 43 в Алматы. Binding-расчёты до Достык, 52 и
Абая, 44 прошли успешно. Создание тестовой доставки без SMS вернуло
`INFO_RECEIVED`, tracking URL был создан, после немедленной отмены заказ получил
финальный статус `REJECTED`. Реальный курьер, еда и оплата не затрагивались.

Расчёт с получением наличных вернул `CASH_ON_DELIVERY_DISABLED`: менеджеру нужно
включить cash collection именно для тестового merchant/venue, если этот сценарий
понадобится позднее. По решению владельца 04.09 наличные не блокируют первую
версию Wolt: через Wolt пока передаются только уже оплаченные заказы. Расчёты до
двух адресов в Экибастузе по-прежнему возвращают `Dropoff location is outside of
the delivery area`; это ожидаемо для алматинского тестового ресторана и не
подтверждает доступность будущего production venue в Экибастузе.

Дополнительная живая проверка development API подтвердила:

- endpoint available venues возвращает один тестовый ресторан для Алматы;
- более дальний адрес Аль-Фараби, 77/8 остаётся внутри зоны и даёт binding quote;
- адрес в Астане отклоняется с `DROPOFF_OUTSIDE_OF_DELIVERY_AREA`;
- отложенная доставка с `scheduled_dropoff_time` принимается;
- время приготовления свыше документированного максимума 60 минут отклоняется;
- повторная отмена уже отменённой доставки безопасно возвращает `REJECTED` и
  пояснение `The order is already cancelled`;
- фактический API, в отличие от текста документации, не принимает только город:
  требует `post_code` либо пару `street + city`.

04.09.2026 создан отдельный Railway environment `staging` с собственной БД и
`POSTER_DRY_RUN=1`. Backend доступен по
`https://backend-staging-088c.up.railway.app`. Тестовые настройки Wolt сохранены
в staging-базе в режиме `test`. Публичный callback
`https://backend-staging-088c.up.railway.app/wolt-drive/webhooks` зарегистрирован
через Wolt API и повторно подтверждён через список webhook: он включён
(`disabled: false`). Запрос без корректной подписи получает `401`.

Режимы разделены жёстко:

- `disabled` — запросы в Wolt не делаются;
- `test` — только `https://daas-public-api.development.dev.woltapi.com`;
- `production` — только `https://daas-public-api.wolt.com` и только после явного
  переключения владельцем.

Merchant Key хранится в базе поарендатно. Админка никогда не показывает его
обратно, только признак наличия и последние четыре символа.

## Оплата

- `CASH`: код умеет передавать сумму к сбору и сумму, с которой нужна сдача, но
  тестовый merchant сейчас возвращает `CASH_ON_DELIVERY_DISABLED`. Сценарий
  сознательно отложен; такие заказы пока остаются у собственного курьера.
- `CARD_ON_DELIVERY`: в первой версии Wolt запрещён. Наш терминал есть у нашего
  курьера, а не у Wolt.
- `KASPI_ONLINE`: будет разрешён только после статуса `PAID`.

Коммерческие тарифы, названные менеджером (984 ₸ за подачу/первый километр,
затем 81 ₸ за 500 м до 5 км и 127 ₸ за 500 м после 5 км; cash-комиссия 2%),
в код не зашиваются. Кассир видит фактическую цену из binding promise.

## Безопасность и сбои

- Все операции tenant-scoped; чужой заказ или чужие ключи не доступны.
- Вызов разрешён только для активной доставки с телефоном и полным адресом.
- При timeout/5xx во время создания заказа автоповтор не делается: запрос мог
  успеть на стороне Wolt, и повтор вызовет двух курьеров. Кассиру показывается
  требование сначала проверить Wolt.
- Автоотмены нет. После начала pickup Wolt может отклонить API-отмену; тогда
  нужно обращаться в поддержку.

## Что готово в коде

- `backend/src/wolt-drive/`: provider, orchestration, validation, test/production host isolation;
- миграция `20260904120000_wolt_drive_foundation`;
- owner-only настройки Wolt Drive в админке;
- фиксированный предел цены по сумме заказа: меньше 6 000 ₸ — 1 200 ₸,
  от 6 000 до 7 999 ₸ — 1 500 ₸, от 8 000 ₸ — 2 000 ₸; блокировка действует
  в UI и повторно на backend;
- окно расчёта, вызова, tracking URL и отмены в кассе;
- audit log для вызова, отмены и изменения настроек;
- публичный `POST /wolt-drive/webhooks`, который принимает только подписанный
  HS256 JWT, сохраняет события идемпотентно и не откатывает статус назад при
  запоздавших событиях;
- owner-only регистрация callback через Wolt API после появления staging URL;
- unit-тесты URL, payload, promise, отмены, адреса, денежного формата и webhook.

Локальная сквозная проверка callback: валидный JWT — `204`, его повтор — `204`
и одна запись в журнале, неверная подпись — `401`.

## Что осталось

1. Пройти через нашу staging-админку: quote, явное подтверждение вызова, tracking,
   немедленную отмену и недоступный адрес.
2. Проверить живые webhook-события и отмену после назначения тестового курьера.
   Прямые API quote, вызов, tracking URL и немедленная отмена уже проверены.
3. Позднее, если понадобится, попросить Wolt включить cash collection и проверить
   наличные со сдачей и без сдачи.
4. Уточнить тариф за ожидание после бесплатных 10 минут, no-show и cancellation fee.
5. Получить от Wolt письменный ответ о допустимом minimum preparation time
   5/15 минут для уже готового заказа, затем зафиксировать production-минимум.
6. После приёмки включить боевой режим.
